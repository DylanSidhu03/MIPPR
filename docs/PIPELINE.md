# MIPPR pipeline plan

Every action needed for the pipeline to work, in order. Check items off as they are finished (edit this file or use the linked issues).

Decisions and project context live in [CLAUDE.md](../CLAUDE.md) (spec v0.4); what the pipeline measures and outputs is in [CLASSIFICATION_SPEC.md](CLASSIFICATION_SPEC.md). Code so far is the Python prototype in [prototype/](../prototype/README.md), which works on the lab's checkerboard photos with an empty-board photo.

*Last updated October 28, 2026.*

## 1. Define scope and classes

**Goal:** Write down exactly what the pipeline decides, so every later step has a target.

**Flow:** Project guidelines -> Class definitions + size rule

- [x] Fix the size cutoff (particles larger than 500 µm) and which dimension it applies to. Decided: longest length (max Feret) is the main size. A particle is flagged for review if its min width is under 500 µm or its longest length is 450–550 µm.
- [x] List morphology classes (fragment, fiber, film, foam, pellet or bead) with a written visual rule for each. Plus "other / unsure"; a fiber is length:width ≥ 3:1.
- [ ] Add 2–3 example photos per morphology class (from the stage 2 pilot batch)
- [x] List color classes: 13 classes. Clear and white are kept separate by a rule; multicolor means a second color covers ≥ 20%.
- [ ] Add a reference swatch and HSV/Lab range per color class (once the color reference is settled in stage 2)
- [x] Decide how 'not plastic' particles are handled and what the output says when the model is unsure. The app doesn't test plastic or polymer, and every export says so. Uncertain particles get `review` / `review_reason` flags. `polymer_confirmed` columns are left for the lab.
- [x] Choose the output table columns and units (µm, µm²) before any code exists. See spec section 6.
- [ ] Measure a printed checkerboard square with a ruler. The notes say 10 mm; the ImageJ results imply 10.07 mm.
- [ ] Later decision: which perimeter method gives the headline circularity (sub-pixel or ImageJ-compatible; spec section 5)

**In:** Lab sorting protocol, current hand-picking notes.  
**Out:** A one-page classification spec every annotator and script follows: [CLASSIFICATION_SPEC.md](CLASSIFICATION_SPEC.md).  
**Watch for:** Hand-picking depends on who is looking. If the class rules stay vague, the labels and the model inherit that disagreement.

## 2. Standardize image capture

**Goal:** Make photos comparable across days, people and labs.

**Flow:** Physical samples -> Calibrated image set

Proposed in spec v0.4: printable backgrounds generated by the website, printed at actual size on matte paper.

- [ ] Pick the imaging setup and lock height, zoom and lighting. Proposed: diffuse even light, no flash, roughly overhead, phone-friendly.
- [ ] Set a minimum photo resolution. The lab's sample photos are about 75 µm/px, so a 500 µm particle is only about 7 px across and fibers under ~150 µm wide are lost. Test closer shots in the pilot batch.
- [ ] Choose the backgrounds. Proposed: white (dark particles), black (light-colored and clear particles) and checkerboard (mixed samples).
  - Plain backgrounds remove the gridline problem.
  - Test whether the checkerboard is still needed (CLAUDE.md open question 1).
- [ ] Choose paper (matte paper or cardstock), and check whether printer black varies enough between printers to matter (open question 1b)
- [ ] Put a scale reference in every frame. Proposed: corner markers (e.g. ArUco) at a known printed size, which also encode the background type, plus a printed 100 mm line to check printer scaling.
  - Four corner markers can't correct lens distortion. The prototype measured about 3 px of error with a single homography. Consider more markers along the edges.
- [ ] Put a color reference in every frame. Proposed: white and grey patches on the background for white balance. Decide whether hue classes also need colored patches.
- [ ] Keep a marked central zone for particles, clear of markers
- [ ] Record pixels per µm for each setup and check it against a ruler image
- [ ] Set file naming and folder layout. The metadata fields are already decided in the spec: sample ID, date, operator, lab, setup, site.
- [ ] Shoot a pilot batch of 50 to 100 particles covering every class

**In:** Filtered, dried samples; microscope or camera.  
**Out:** Images with a known scale and color reference, plus a metadata sheet.  
**Watch for:** Glare, shadows and clear particles on a bright background hide edges. Fixing this at capture is cheaper than fixing it in code.

## 3. Build the labeled dataset

**Goal:** Create the ground truth that both trains and judges the pipeline.

**Flow:** Pilot images -> Labeled masks + class tags

- [ ] Find out whether a labeled set already exists from past hand-classification (open question 4)
- [ ] Choose an annotation tool (CVAT, Label Studio or similar) and set it up with the class list from the spec
- [ ] Outline particles and tag color and morphology on at least 300 particles
- [ ] Have a second person label a 20% subset independently
- [ ] Measure agreement between labelers (Cohen's kappa for classes, overlap for outlines)
- [ ] Resolve disagreements and update the class spec from what you learn
- [ ] Split into train, validation and test sets by sample, not by image

**In:** Pilot images, class spec.  
**Out:** Versioned dataset with a held-out test set and a measured human agreement ceiling.  
**Watch for:** The model cannot beat the agreement between humans. Measure that number early so the accuracy target is realistic.

## 4. Preprocess images

**Goal:** Turn raw photos into consistent, calibrated images.

**Flow:** Raw images -> Normalized images

- [x] Correct perspective and lens distortion (checkerboard). Each square is warped onto a fixed grid using its own four corners, which brings alignment error from about 3 px down to 0.1 px.
- [ ] Correct perspective from corner markers (plain backgrounds)
- [x] Correct uneven illumination (checkerboard + empty template). The template is brightness-matched to the photo square by square. In the sample, blacks were 3× brighter in one shot.
- [ ] Correct uneven illumination without a template photo (plain backgrounds)
- [ ] Normalize white balance and color using the reference patches
- [x] Convert to a standard color space (LAB) for color work. CIE Lab, HSV and RGB are measured per particle.
- [x] Read the scale from the checkerboard to get µm per pixel. The fixed grid gives µm/px = square size / px per square.
- [ ] Read the scale from the corner markers and the 100 mm check line
- [x] Write unit tests on a few known images. Synthetic boards with known particles, tilt and exposure change.

**In:** Raw images and metadata.  
**Out:** Normalized images and a µm-per-pixel value for each.  
**Watch for:** Color class accuracy depends on this step. A wrong white balance moves particles across color classes.

## 5. Segment particles

**Goal:** Find every particle and separate touching ones.

**Flow:** Normalized images -> Particle masks

- [x] Build a classical baseline: template difference, hysteresis threshold, half-maximum edge placement
- [ ] Score the baseline on the validation set. So far it has only been compared with ImageJ: 24 of 24 particles found and no false detections on the fragment_area sample.
- [ ] Try a learned segmenter (Cellpose, SAM or a small U-Net) and compare against the baseline
- [x] Handle gridlines bleeding into outlines. Thin slivers along the gridlines are ignored, and the difference is bridged where a particle crosses a printed edge.
- [ ] Handle touching and overlapping particles, and thin fibers that break into pieces
- [ ] Handle translucent films and clear particles. Low-contrast outlines are flagged for review for now.
- [x] Remove debris, dust and edge artifacts with area and shape rules: a minimum area, a board-edge margin, and the gridline sliver rule
- [x] Write out an overlay image of outlines on the photo for every input
- [ ] Segment on plain white and black backgrounds (no template photo)

**In:** Normalized images, labeled masks.  
**Out:** One mask per particle and a QC overlay image.  
**Watch for:** Fibers and clear particles are the usual failures. Look at failures by class, not only the average score.

## 6. Measure size and shape

**Goal:** Produce standardized numbers in µm.

**Flow:** Particle masks + scale -> Measurement table

- [x] Compute area, equivalent diameter, longest and shortest axis (Feret), and aspect ratio. Also perimeter, convex area/perimeter, bounding boxes, circularity and solidity.
- [x] Compare perimeter methods on shapes with a known answer. The sub-pixel outline is most accurate; ImageJ-compatible values are kept alongside (provisional).
- [ ] Measure fiber length along the skeleton instead of the bounding box
- [x] Convert pixels to µm and µm² with the stored scale
- [x] Apply the 500 µm cutoff and flag particles within 10% of it for review (also flags min width < 500 µm)
- [x] Compare automated sizes with the lab's ImageJ results. Median differences across 24 particles: area +0.5%, Feret −0.2%, min Feret +0.1%.
- [ ] Compare automated sizes with manual caliper or microscope measurements on 50 particles

**In:** Masks, µm-per-pixel value.  
**Out:** One row per particle with size and shape columns.  
**Watch for:** A scale error shifts every particle across the 500 µm line, so check calibration before trusting counts.

## 7. Classify color and morphology

**Goal:** Replace the visual judgment call with a repeatable rule or model.

**Flow:** Masks + normalized image -> Color and morphology labels

- [x] Extract mean color per particle in LAB (and RGB, HSV), ignoring edge pixels. Mean and SD only so far.
- [ ] Extract dominant color and second-color share per particle (needed for the multicolor rule)
- [ ] Map color to classes with rules (v2) fitted on the labeled set. Use clustering or a small classifier if rules fall short.
- [ ] Classify morphology from shape features (aspect ratio, solidity, skeleton length) with a baseline model
- [ ] Try a CNN on particle crops if the feature model falls short (v3). Compare a classifier chain with one multi-task model.
- [ ] Output a confidence score and send low-confidence particles to a review list. Review flags already exist for size and outline quality.
- [x] Decide how plastic versus non-plastic is flagged, and state plainly what the images cannot tell you. The app doesn't test plastic or polymer, and every export says so.

**In:** Masks, images, labeled dataset.  
**Out:** Color, morphology and confidence columns added to the table.  
**Watch for:** Images alone cannot confirm a particle is plastic. Keep a human review path and say so in the output.

## 8. Validate against people

**Goal:** Show the pipeline is good enough to trust, with numbers.

**Flow:** Test set + pipeline output -> Accuracy report

- [ ] Agree how close to hand measurements counts as validated (open question 6)
- [ ] Run the pipeline once on the held-out test set and do not tune on it
- [ ] Report detection recall and precision, class confusion matrices, and size error in µm
- [ ] Compare model-versus-human agreement with human-versus-human agreement
- [ ] Count how many particles land in the review list
- [ ] Time the manual workflow against the pipeline on the same batch
- [ ] Run a small test on images from a second setup or lab

**In:** Held-out test set, human agreement numbers from the dataset stage.  
**Out:** A short report with a pass or fail against targets set at the start.  
**Watch for:** A model that works only on the pilot setup is not a standardized method. The second-setup test shows whether it generalizes.

## 9. Batch run and outputs

**Goal:** Process a whole folder with one command and get tidy results.

**Flow:** Folder of images -> CSV + QC overlays + summary

- [ ] Wrap the stages into one command that takes a folder and a settings file. The prototype CLI handles one particle/template pair at a time.
- [x] Write a per-particle CSV and QC overlays (columns as in the spec, plus `NOTE.txt`)
- [ ] Write per-sample summary counts
- [x] Log versions, settings and scale used for every run so results can be reproduced (`run.json`)
- [ ] Handle bad inputs (missing scale, blurry image) with a clear message instead of a crash. So far only "board not found" is handled.
- [ ] Time it on 500 images and fix the slowest step. About 5 s per photo pair so far.
- [x] Write a README with install steps and a worked example ([prototype/README.md](../prototype/README.md))

**In:** Image folder, settings file.  
**Out:** A command-line tool that others in the lab can run.  
**Watch for:** If it is hard to install, nobody outside the project will use it.

## Decision point: build the web app?

Go only if validation met its targets, the batch tool runs for someone other than you, and there is a hosting and maintenance plan. Otherwise release the command-line tool and documentation as the finished project.

The stack is already decided (CLAUDE.md): a static site on GitHub Pages, with OpenCV.js and ONNX Runtime Web in the browser. No server, and photos never leave the user's computer. The release plan builds the app in stages (v1 measurement, v2 color rules, v3 morphology model, v4 label contributions), so this decision applies to each release.

- [ ] Validation targets met
- [ ] A second person ran the batch tool without help
- [ ] Hosting and upkeep plan agreed (who maintains it after the practicum: open question 7)

## 10. Open-source web app (if feasible)

**Goal:** Let researchers and community scientists use the pipeline in a browser.

**Flow:** Uploaded images -> Downloadable results

- [ ] Sketch the screens: print background, upload, set scale, run, review, export
- [ ] Generate the printable backgrounds (PDF, Letter and A4; white, black and checkerboard, with corner markers and a 100 mm check line)
- [ ] Port segmentation and measurement to OpenCV.js
  - Check that the OpenCV.js build includes the ArUco module, or use a custom build or a JS marker library.
  - Write a marching-squares step for the sub-pixel perimeter, which OpenCV.js lacks.
- [ ] Run batches in the browser on the user's machine (no server or job queue)
- [ ] Build the upload and progress screens, and a results table with overlays
- [ ] Add a review screen where a person can reject false detections and correct a class or outline, with the correction saved
- [ ] Support scale entry for users without the printed background, with clear guidance on how to take the photo
- [ ] Warn when a photo is blurry, too dark, or missing the scale reference
- [ ] Export CSV and the overlay image, plus a PDF or HTML summary
- [ ] Let users export corrected labels as a file to submit for the dataset (v4)
- [ ] Choose a license, add contribution notes and tests, and set up automated builds
- [ ] Host on GitHub Pages; set upload size limits and a data retention policy (photos stay on the user's machine)
- [ ] Pilot with two or three outside users and collect what confused them

**In:** Batch tool, accuracy report.  
**Out:** A hosted app and a public repository.  
**Watch for:** Community photos will vary far more than lab photos. Plan for quality checks on upload and for retraining with corrected labels.

## 11. Document and release (if feasible)

**Goal:** Make the method citable and reusable.

**Flow:** Everything above -> Public release

- [ ] Agree the data license and consent terms for contributed photos and labels (open question 9)
- [ ] Publish the labeled dataset or a sample, with a data card (e.g. on Zenodo for a citable DOI per version)
- [ ] Write the methods page: class definitions, calibration, accuracy and known limits
- [ ] Tag version 1.0 with a changelog
- [ ] Draft a short paper or report and share the repository with the lab group
- [ ] Set a plan for who answers issues and retrains the model, with gated retraining against a fixed gold test set

**In:** Validated pipeline, documentation.  
**Out:** Tagged release and methods write-up.  
**Watch for:** Without stated limits, users will over-trust the output.
